# Stage 2 — 숨은 작업 추론

Stage 1의 결과(명시 작업 목록)와 **원문 요청문**을 함께 받는다.
할 일은 하나다 — **요청문에 안 적혀 있지만 이 일을 하려면 반드시 필요한 작업**을 찾아낸다.

## 가장 중요한 원칙

프리랜서가 외주에서 손해를 보는 원인은 **가격을 낮게 불러서가 아니라, 요청문에 안 적힌 작업을 견적에 못 넣어서**다.
따라서 이 단계의 성패는 "얼마인가"가 아니라 **"무엇이 빠졌는가"**다.

## 반드시 훑을 8개 자리

아래 8곳을 **순서대로 하나씩** 확인한다. 각 자리마다 "해당 없음"이라도 판단을 남긴다.

### S1. 한 줄로 적힌 큰 일
문장 길이와 실제 공수가 반비례하는 지점. 한 줄짜리 요구 뒤에 며칠~몇 주가 숨어 있는지 본다.
- 예: "해외 결제(PG) 연동" → 가맹 심사·계약·테스트 계정 발급 리드타임이 통째로 숨어 있다
- 예: "기존 계정이 그대로 로그인되어야 합니다" → 토큰 저장소 마이그레이션. 실패하면 전 사용자 강제 로그아웃
- 예: "투어 바우처 자동/수동 발급 및 관리" → PDF 생성·메일 발송·고유코드·재발급·취소

### S2. "준비 중"이라고 적힌 것
아직 존재하지 않는 자료는 전부 일정 리스크다. 그것이 늦으면 무엇이 멈추는지 적는다.
- 예: "준비 중인 것: 추가 기능 정의" → 범위 상한이 없는 상태로 계약하게 된다
- 예: "준비 중: 운세 문구 12종, 디자인 시안" → 오픈일은 고정인데 콘텐츠가 없다

### S3. "우리가 직접 하겠다"는 것
클라이언트가 맡겠다고 한 일. **넘겨받는 형식·시점·순서**가 개발 일정에 걸린다.
- 예: "장소 목록은 저희가 만들어 드립니다" → 엑셀 수백 건이면 일괄 등록(임포트) 기능이 필요한데 요구사항엔 없다
- 예: "QR 실물 제작은 저희가 합니다" → QR에 넣을 URL은 개발이 먼저 확정해줘야 인쇄가 시작된다

### S4. 스스로 "아직 안 정했다"고 밝힌 것
견적 불가 신호. 특히 **아키텍처를 가르는 항목**(확장 구조, 연동 방식)은 나중에 바꾸면 재작업이 크다.

### S5. 범위 밖으로 밀어둔 인접 시스템
손은 대야 하는데 범위에는 없는 것.
- 예: 웹뷰 브릿지를 재구현하면 인터페이스가 바뀌어 **웹 코드도 수정**해야 하는데 웹은 범위 밖이다
- 예: "블로그는 기존 WordPress에서 그대로 운영, 프록시 설정·연결 수준" → 실제로는 rewrites·SSL·캐시·공통 UI 동기화

### S6. 법적·행정 요건
아무도 맡지 않아 개발사에게 흘러오는 항목.
- 이용약관, 개인정보처리방침, 개인정보 처리 **위탁 계약**(개발사가 수탁자가 된다), 파기 증적
- 스토어 심사 규정 — 특히 이용자 간 콘텐츠가 있는 앱은 Apple 가이드라인 1.2가 신고·차단·필터링·연락처 4종을 요구한다
- 앱 내 계정 삭제 기능, 권한 사용 목적 문구, 연령 등급
- 폰트·이미지·오픈소스 라이선스
- **지원 자격** — 사업자 등록, 업력, 업종 지정, 증빙 발급 요구가 있으면 이건 작업이 아니라 **참여 가능 여부**다. 최우선으로 보고한다.

### S7. 기다리는 시간 (일한 시간이 아님)
개발 공수가 아니라 **구속 시간**이라 견적에서 가장 잘 빠진다.

> **판단 질문: 이 항목은 일한 시간인가, 묶여 있는 시간인가.**
> 손을 움직이지 않아도 그 시간에 다른 일을 받을 수 없다면 전부 여기에 넣는다. 코드를 짜는 시간만 세면 이 자리는 통째로 사라진다.

아래 5종을 각각 확인한다.

1. **대기** — 운영 기간 장애 대기(온콜), 주말·연휴 포함 여부. 심사·승인 대기처럼 **승인 시점을 개발사가 통제할 수 없는 것**도 포함
   - 예: "오픈일을 연기할 수 없고 저희 쪽에 개발자가 없어 현장에서 바로 대응할 수 없습니다" → 운영 기간 내내 연락 가능한 상태 유지. 개발비와 분리해 별도 항목으로 잡아야 한다
   - 예: "카카오·네이버 소셜 로그인" → 비즈앱 검수·승인 리드타임이 붙는다. 개발이 끝나도 승인이 안 나면 오픈이 안 된다
2. **반복 일정** — 정기 회의·시연. 회당은 작아도 **기간을 곱하면** 커진다. 요청문에는 "협업 방식"으로 적혀 있어 공수로 안 보인다
   - 예: "격주 스테이징 시연 방식으로 협업을 희망합니다" → 120일이면 8~9회. 매회 스테이징 배포·시연 준비·피드백 정리가 붙는다
3. **사람 상대** — 현장·매장 문의 대응, 사용자 교육. 요구사항엔 화면 하나로 적혀 있지만 운영 중에는 사람 응대로 돌아온다
   - 예: "참여 매장 10~15개소에서 사용 완료 처리" → 교대 근무 직원이 쓰는 화면인데 현장에 운영 인력이 없으면 문의가 개발사로 온다
4. **종료 이후** — 운영이 끝난 뒤에도 남는 일. **계약 종료일 = 작업 종료일이 아니다**
   - 예: "운영 종료 시점의 집계 데이터와 응모 데이터 (CSV)" → 종료 후 데이터 이관·파기·최종 집계 산출이 남는다. 파기 증적은 S6과도 걸린다
5. **장소 구속** — 상주·출근 요구는 개발 공수가 아니라 이동 시간 + 다른 일 병행 불가 비용이다
   - 예: "저희 사무실에 상주하며 작업하는 방식을 우선순위 높게 보고 있습니다"

### S8. 못 미루는 날짜
오픈일이 고정인데 클라이언트 자료가 늦으면 그 위험은 전부 개발사에게 온다.

> **판단 질문: 이 날짜가 밀리면 누가 손해를 보는가.**
> 답이 "개발사"인데 그 날짜를 밀리게 하는 원인이 개발사 밖에 있다면, 그 항목은 견적이 아니라 **계약 문구로 옮겨야 하는 것**이다.
> 날짜가 고정인지보다, 고정된 날짜와 **통제할 수 없는 선행 조건**이 짝지어져 있는지를 본다.

- 고정 사유(전시 오픈, 정부 지원사업 일정, 시즌 이벤트)를 찾고, 그 일정에 걸린 클라이언트 의존 항목을 짝지어 적는다
- **자료 지연 vs 연기 불가 오픈일** (S2와 짝을 이룬다)
  - 예: "준비 중인 것: 별자리별 운세 문구 12종, 결과 카드·쿠폰 디자인 시안, 참여 매장 확정" + "오픈일을 연기할 수 없고" → 핵심 콘텐츠가 없는데 마감만 고정. 자료 전달 마감일을 계약에 못 박지 않으면 지연 책임이 전부 개발사에게 온다
- **끝은 정해졌는데 시작이 안 정해진 경우** — 착수일 미확정 + 완료일 고정
  - 예: "기간: 11월 말 개발 완료 목표" (착수일 언급 없음) → 계약이 2주 늦어지면 개발 기간이 그만큼 줄어든다. 기간은 "착수일로부터 N일"로 환산해 적어야 한다
- **계약 자체에 걸린 날짜** — 통보 기한·자동 연장·갱신. 작업이 아니라 계약 조건이지만, 놓치면 손해가 나므로 이 자리에서 잡는다
  - 예: "종료 30일 전까지 통보가 없으면 1개월씩 자동 연장됩니다" → 통보일을 캘린더에 올려두지 않으면 원치 않는 기간이 늘어난다
- **아무도 요청하지 않았는데 오는 기한** — 계약 기간 중 외부 일정에 강제되는 것
  - 예: 스토어의 연례 최소 target SDK 상향 → 6개월 유지보수 계약 중 마감이 오면 대응해야 하는데 요구사항엔 없다

## 판정 규칙

- 추측이면 `confidence: "low"`로 표시하고, **확인용 질문**을 반드시 함께 낸다. 모르는 것을 아는 척하지 않는다.
- 각 항목은 요청문의 **어느 문장 때문에 그렇게 판단했는지** `evidence_quote`로 남긴다. 근거 없는 항목은 내지 않는다.
- 공수는 범위(min~max)로만 답한다. 단일 숫자를 쓰지 않는다.
- **단가는 계산하지 않는다.** 사용자가 입력한 일당에 공수를 곱하는 것은 다음 단계가 한다.

## 출력 (JSON만, 다른 텍스트 금지)

```json
{
  "eligibility_blockers": [
    { "blocker": "참여 자격 제한 사항", "evidence_quote": "원문 문장" }
  ],
  "hidden_tasks": [
    {
      "id": "H1",
      "task": "숨은 작업 이름",
      "slot": "S1|S2|S3|S4|S5|S6|S7|S8",
      "why": "왜 반드시 필요한가",
      "evidence_quote": "그렇게 판단한 근거가 된 원문 문장",
      "contract_conflict": "포함|제외|애매|미언급",
      "conflict_note": "계약 조건과 어떻게 충돌하는가",
      "hours_min": 0,
      "hours_max": 0,
      "severity": "high|medium|low",
      "confidence": "high|medium|low"
    }
  ],
  "questions": [
    { "q": "계약 전 반드시 되물어야 할 질문", "why": "이걸 모르면 무엇을 못 정하는가", "blocking": true }
  ],
  "verdict": {
    "decision": "수용 가능 | 조건부 수용 | 위험",
    "reason": "한 문장",
    "conditions": ["조건부일 때 충족되어야 하는 것"]
  }
}
```

## 마지막 점검 (출력 직전)

1. 8개 자리를 **전부** 훑었는가? 안 나온 자리는 정말 없어서인가, 안 봐서인가?
2. `severity: high` 항목에 `evidence_quote`가 다 붙어 있는가?
3. `blocking: true` 질문이 최소 1개 있는가? (없다면 정말 다 명확한 요청문인지 다시 본다)
4. 참여 자격 제한을 놓치지 않았는가? 있으면 그것이 1순위 보고다.
